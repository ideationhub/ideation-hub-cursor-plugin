# Assumptions, open questions and future enhancements

## Assumptions

1. **Existing types are enough for a first version.** Decisions, interfaces and data models are stored as SD or CD records distinguished by `arch.*` tags. No server or schema change is needed.
2. **The credential decides whether a write is live.** With direct edit, Ideation Hub's propose tools write living records unless `mode: "suggest"` is passed, so the skill always passes it unless the user explicitly asks for a direct write.
3. **Link direction must be checked by the agent.** Ideation Hub's bulk dry run checks that link ends exist but not their direction, so the skill checks direction itself.
4. **Test links:** Verification Tests (VER) and Unit Tests (UT) verify designs; Validation Tests (VT) check User Needs and Business Needs.
5. **`design_ready` is per Product Requirement.** Development-phase events are recorded against requirements, so the handoff records one event for each in-scope Product Requirement.
6. **Search may be keyword-only.** When Ideation Hub's hybrid search is not active, retrieval relies on keywords and tags, so the skill favours tag and ID reads.
7. **Accepted vs pending.** Records with status `proposed` or `approved` are accepted; `unapproved` is pending.

## Open integration questions

1. **Link direction at creation.** Should Ideation Hub reject direction-invalid links at creation time (and in dry runs) rather than relying on agents?
2. **Design interactions.** "A calls B" lives only in record text. Is that acceptable until a link type exists?
3. **`design_ready` for draft designs.** Handoff always records the event. Should it also be recorded when the design is still pending acceptance, or should the server reject it in that case?
4. **Tag vocabulary.** Should the `arch.*` tags be reserved or suggested in the Ideation Hub UI?
5. **Requirements skill alignment.** The requirements skill's allowed-trace list should state the same test-link rule as `references/traceability.md`.

## Future enhancements

These need product requirements first; this skill does not ask for them.

1. **Decision record type** (or a structured decision field set on SD), with status and a "supersedes" relation.
2. **A `depends_on` (or `interacts_with`) link type** between design records, so component interactions can be queried and impact walked through them.
3. **A supersede lifecycle action** that sets `superseded` and `supersededById` instead of obsolete + new record.
4. **Interface and data model types** with structured fields (operations, schemas).
5. **Server-side design checks:** coverage, orphan and staleness reports from an MCP read tool.
6. **Diagram view** generated by Ideation Hub from SD/CD records.
7. **A Codex plugin manifest** once the plugin format is settled for this repository.
